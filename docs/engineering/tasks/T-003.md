# T-003 — Registro compartido de features

- Dueño: Codex
- Estado: done; pendiente de merge humano
- Rama: `feature/t-003-feature-registry`
- Módulos permitidos: `AGENTS.md`, `README.md`, `package.json`, `docs/engineering/FEATURES.md`, `docs/engineering/features/F-003.json`, `docs/engineering/tasks/T-003.md`, `scripts/features.mjs`, `scripts/features.test.mjs`, `.github/workflows/ci.yml`. La creación inicial de F-001, F-002 y F-004 a F-013 es parte del bootstrap, pero no los reserva para Codex después de la PR.
- Objetivo: mantener un backlog basado en el roadmap del MVP, legible por humanos y agentes, con asignación y estados visibles antes del merge.

## Contrato

Cada feature vive en `docs/engineering/features/F-###.json` y conserva `id`, `name`, `title`, `description`, `plan`, `acceptance`, `sdd`, `status`, `roadmap_note`, `owner`, `ticket`, `branch`, `pr`, `depends_on`, `allowed_modules`, `reviewed_by` y `evidence`. Un script genera la lista a partir de esos archivos y valida el esquema, las dependencias y los requisitos de cada estado sin reescribir otros features. Las transiciones se editan en el JSON del feature.

Estados: `pending → claiming → in_progress → in_review → done → merged`; `blocked` puede usarse desde un estado activo y volver a `in_progress`. `claiming` cubre el intervalo de publicación de la draft PR; desde `in_progress` la PR es obligatoria. `done` significa implementación, gates, revisión ajena y PR listos; solo el humano puede fusionar la PR a `main` antes de registrar `merged`.

## Aceptación

- Backlog inicial trazable a la fundación, integración de Mercado Libre y roadmap de README.
- Cada agente puede reclamar un feature con dueño, ticket, rama y módulos permitidos antes de editar código.
- Dos agentes en features diferentes no tienen que editar el mismo registro de estado.
- Listado y validación reproducibles en CLI y gate de CI.
- T-003 registra comandos, resultados, archivos, riesgos y siguiente paso; se abre PR sin fusionarla.
